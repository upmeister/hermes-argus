## 1. Outcome / boundaries

Vlad authorizes an opt-in `MODULE_LOCAL_SERVICES` (OFF by default), with a read-only schema-1 local-topology producer and comparison of an **operator-authored expected-target manifest**. It checks **only two `systemd --user` targets selected on Vlad's host** (`2ch-monitor.service`, `nail-bot.service`), reporting status in the Telegram bot when its UI module is enabled, and alerting on confirmed degradation in the first feature slice. The two personal names are examples in the operator document; they must **not** be checked on every public install or discovered automatically as expected targets. No service start/stop/restart controls, arbitrary plugins, Docker/system units as targets, generic framework, or change to the existing SearXNG integration.

PR #54's snapshot has `schema: 1`, `generated_at`, `services.user/system`, containers, listeners, resources and `reboot_ready`. It is an observed inventory, **not** the manifest of expected services. Do not conflate `enabled` or systemd `inactive` on an unselected unit with an outage. `active` proves systemd state only, not application semantics. Read Argus `AGENTS.md`, current tests and ADR 0001; STOP for Vlad if this requires an unapproved new subsystem, extra production entrypoints, persistent format, dependency, or unrelated refactor. The explicitly authorized narrow alert state needed for hysteresis is in scope, but not a general alerting framework.

## 2. Flag and full producer lifecycle

Canonical flag is `MODULE_LOCAL_SERVICES`, default `OFF` even when unset. The accepted behavior is **OFF means no collection, no comparison, no local-service alerts and no navigation**, including after ON → OFF on a running installation. ON installs/activates the collector from PR #54 and schedules production of a *new* atomic snapshot every 5 minutes. The consumer should run after collecting each time; the module can use a single bounded sequential job instead of competing unsynchronized cron jobs. Prompt initial collection on activation (after prerequisites/deploy have succeeded), so users don't wait for a preexisting snapshot. Limit and report collector failure; never turn it into successful empty inventory.

**Important inherited gap:** PR #54 conditionally *generates* a collector line in `/tmp/hermes-argus-crontab.txt`, but `deploy.sh` currently does not own/reconcile the user's live crontab. A previously manually installed line may run even after the flag is turned OFF; an already stored snapshot may persist. The builder must verify OFF on a real ON → OFF transition, not just the default config. Use the narrowest safe owned-cron reconciliation or runtime guard; preserve unrelated user crontab. Explicitly surface failures and STOP if correct ownership requires a wider installer/cron redesign; do not falsely claim OFF works. Do not delete other module state or install a scheduler framework. Deleting the old snapshot on OFF is not necessary if every reader is gated and no collector runs; old snapshots on re-enable are `unknown` until a fresh collection.

`MODULE_TG_BOT` controls interactive UI independently. If local services ON and Telegram bot OFF, the headless local check still runs and attempts alerts using existing configured delivery; no button exists. Missing Telegram credentials/delivery is reported as an operational gap, never a claimed successful notification. Public default install remains OFF even if CORE is ON.

## 3. Expected-target manifest and source validation

Proposed operator-owned file: `~/.config/hermes-argus/local-services.json` (freeze this path before coding). Deploy never overwrites it; config is not committed as production data. Strict v1 JSON:

```json
{
  "schema": 1,
  "targets": [
    {"id": "2ch-monitor", "label": "2ch monitor", "source": "systemd_user", "name": "2ch-monitor.service", "expect": "active"},
    {"id": "nail-bot", "label": "Nail bot", "source": "systemd_user", "name": "nail-bot.service", "expect": "active"}
  ]
}
```

Only listed targets are checked. Empty/missing manifest is an **unconfigured** onboarding condition, not "all healthy". Validate file size, UTF-8/JSON/schema version, exact supported keys/source/expect, unique IDs and `(source,name)`, service-name shape, bounded labels/count, control characters and type correctness. No arbitrary shell/command, path imports, automatic promotion from snapshot or network probes.

For the snapshot validate bounded read, `schema == 1`, timezone-aware `generated_at` not in future, freshness budget (proposed **12 minutes** with 5-minute collection), `services.user` structure/fields and source error markers; account for a collector exception before comparison. Some producer commands return empty output; schema 1 does **not** prove a successful exhaustive unit enumeration. If the target is absent from an otherwise valid snapshot, treat it as **unknown**, not positive failure or health; explicitly report suspected missing unit to operator. To distinguish confirmed unit-not-found from unavailable source would require positive evidence and an approved narrow producer/schema change. Never infer user-service health from container/listeners, `reboot_ready`, `enabled`, or the age of an unrelated report.

Verdicts: `healthy` = fresh valid explicit target row `active`; `failed` = fresh valid explicit target row `inactive`/`failed` under expectation `active`; `unknown` = stale, unreadable, malformed, unsupported, producer unavailable or target missing/inconclusive. Unknown **never** clears an alerted failure. Corrupt manifest is configuration error and visible as such. Record stable target IDs separately from display labels. Never auto-recover because a check disappeared or module was disabled.

## 4. Alert semantics, distinct observations and failure visibility

Production loop every **5 minutes** after a collection attempt. For each expected service, send the first degradation alert after **two consecutive *different fresh snapshots*** showing `failed` (distinct `generated_at`/observation identity); typically ~10 minutes, timing dependent on collection and scheduling. The same cached snapshot re-read twice is one observation, not two failures. For an alerted failure, one fresh positive `healthy` snapshot permits one recovery message and resets the counter; an `unknown` or unreadable source preserves failure state and does not assert recovery. Repeated identical failure must not spam Telegram; opt-in bounded reminder policy may be deferred, not invented from integration wrapper's 12-run cadence. Prevent double counting if job overlaps or restarts; a tiny atomic, module-owned state file per target with last observation identity/alerted status is authorized, not a generic DB.

**Blind monitoring** must not be silent: a missing, stale, malformed or failed producer after targets are configured shows `unknown` in UI and a bounded, deduplicated operator diagnostic on persistent unknown (two separate scheduled collection attempts recommended), without pretending that this is an observed service outage. Transition out of blind state sends a bounded recovered-observation message only when real new evidence exists; service recovery still requires `healthy`. Define and test interaction between diagnostic alert and service-failure alert, mute/silence and delivery retries. No alert if module OFF, no alert for manifest absent/empty; prior pending states must not leak stale recovery when re-enabled. Reuse current Telegram transport/notification policy where suitable; HTTP send attempted ≠ delivery accepted. Log failures safely without secrets, JSON dumps or host topology.

## 5. Telegram UX and auth

When both modules are ON, add one reply-keyboard navigation button `🖥 Локальные сервисы` (visible short label may be localized later) and `/services`. Render only the explicitly selected targets, snapshot timestamp/age, observed systemd state, and clear unknown/error reason, not raw JSON, listening sockets, container inventory or addresses. "Refresh" re-reads the cached snapshot, never launches a system probe; constrain/escape all output for Telegram. Distinguish (a) missing/empty manifest or no uploaded JSON **before configuration** → brief onboarding + stable link to this repo's `docs/local-services.md`, (b) configured manifest + missing snapshot → monitoring unknown/blind, not empty success; (c) malformed JSON/source I/O → bounded operator-readable error, no bot crash. Leave existing `/integrations_all`/SearXNG alone.

After successful ON/OFF application, the running bot must **send a new message containing a new `ReplyKeyboardMarkup`** to refresh the keyboard. A config write, deploy exit or silent message cannot retract an existing Telegram keyboard. `scripts/monitoring-bot-poller.py` currently has static `REPLY_LABELS`, `/start` sends markup, while `webhook.py` toggles MODULE_* in config, launches background deploy and does not reload poller. Tests must verify actual effective module state vs config, completion and restart/reload strategy, timing of outgoing markup, toggle failure/reporting, ON → OFF → ON, and stale `/services` label/command rejection while disabled. Future convention: module-dependent reply navigation appears iff its module is enabled; do not retrofit unrelated modules in this PR.

Current `WATCHDOG_ALLOWED_USER_ID` empty opens the bot; local host status is sensitive. For this feature, **fail closed** if operator allowlist is unset and for unauthorized users, without silently redesigning global auth or leaking paths/snapshot/error payloads to a public user. Report this precondition in onboarding and tests. Maintain existing routes unless directly required for this feature.
